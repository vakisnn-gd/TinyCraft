# TinyCraft — правила для Codex

TinyCraft — voxel-игра на Java/LWJGL. Пользователь учится программированию, поэтому изменения должны быть небольшими и понятными.

## Главный принцип

- Один запуск Codex — одна конкретная задача и один сфокусированный diff.
- Если запрос большой, выполнить только ближайший законченный этап.
- Перед правкой коротко объяснить цель и причину изменения.
- Не переписывать рабочую систему ради рефакторинга или красоты.
- Не выполнять unrelated cleanup.
- Текущие задачи и баги хранить в `ROADMAP.md` и `KNOWN_ISSUES.md`, а не расширять этот файл.

## Перед изменениями

1. Выполнить `git status --short`.
2. Посмотреть изменяемые файлы и связанные тесты.
3. Убедиться, что рабочие изменения пользователя не будут затёрты.
4. Сформулировать один проверяемый результат текущей задачи.
5. Сделать минимальное полезное изменение.
6. Запустить самую короткую подходящую проверку.

## Рабочая папка и Git

- Считать все существующие изменения пользовательскими, пока не доказано обратное.
- Не откатывать и не перезаписывать чужие изменения.
- Не менять файлы, не относящиеся к текущей задаче.
- Не удалять `saves`, `release`, `backups` и `logs` без отдельного разрешения.
- Не добавлять в Git сохранения, логи, IDE-файлы, временные сборки и случайные архивы.
- Не создавать commit, branch, push или PR без прямой просьбы пользователя.
- Перед завершением повторно проверить `git status --short` и назвать изменённые файлы.

## Технические границы

- Не менять формат миров, `player.dat` или сетевой протокол без явной необходимости и совместимого чтения старых данных.
- Новые поля метаданных должны быть необязательными и иметь безопасное значение для старых миров.
- В multiplayer сервер остаётся источником истины для команд, режима, инвентаря и действий с блоками.
- Клиентские проверки не заменяют серверную проверку прав и входных данных.
- Система воды и лавы уже существует: исправлять конкретные ошибки, а не писать жидкости заново.
- При изменении mesh учитывать соседние чанки/секции и не убирать корректный старый mesh до готовности нового.
- Генерацию мира проверять на фиксированном seed; существующие чанки не перегенерировать автоматически.
- Оптимизировать только воспроизведённое узкое место и проверять, что поведение игры не изменилось.
- Лаунчер развивается в отдельном репозитории; не менять его без отдельной задачи.
- VPS не настраивать до стабильной проверки dedicated server через `localhost`.

## Приоритет работы

1. Стабильная сборка и запуск.
2. Критичные баги и дыры рендера.
3. Сохранение, права команд и надёжность gameplay.
4. Небольшие законченные улучшения мира и интерфейса.
5. Оптимизация подтверждённых узких мест.
6. Локальный multiplayer/dedicated server, затем VPS.

## Проверки

- Для Java-логики использовать `run-tests.bat` или `run-tests.sh`.
- Для рендера и ввода дополнительно требуется короткая ручная проверка в игре.
- Для генерации фиксировать seed и координаты проблемного места.
- Для сервера проверять запуск, подключение к `localhost`, `save`, `stop` и повторный вход.
- Не ослаблять и не удалять тесты ради зелёного результата.
- Не объявлять задачу выполненной, если проверка упала или не запускалась; честно указать причину.

- Как проверено.
